# Atelier features

The README covers installing, running and testing atelier. This page lists what the composer, the agent and the CLI can do beyond plain chat, with the limits and safety details of each. Every item is covered by tests; none has been exercised against a live model yet.

Typing `/` in the composer opens a slash-command menu (Arrow keys, Enter or Tab to choose, Esc to dismiss). Built-ins act without sending a message to the model, except `/init`, which sends a fixed prompt: `/plan`, `/build`, `/new`, `/compact`, `/fork`, `/undo`, `/init`, `/instructions`, `/model`, `/skills`, `/skill-new`, `/export`, `/terminal` and `/theme`. Custom prompts are markdown files in `.atelier/commands/` (or `.claude/commands/`, which atelier also reads; `.atelier` wins on a name clash), served by `GET /api/commands`: an optional `description:` frontmatter line labels the entry, `$ARGUMENTS` is replaced by whatever follows the command (or appended when absent), at most 100 files of 20 KB each; an unknown `/name` is refused with a notice instead of being sent to the model.

Files named with `@path` in a prompt are attached on send: the server appends their contents (at most 5 files, 12,000 characters each, workspace paths only; directories and unknown paths are ignored) inside `<attached_file>` blocks, the transcript and markdown export show them as file chips instead of dumping the text.

In Plan mode, once the agent has replied and no run is working, a Build this plan bar appears above the composer; its button switches to Build mode and sends an implement-the-plan prompt, and every edit still waits for your approval.

`/compact` summarises the open conversation with the configured provider (`POST /api/sessions/:id/compact`: the newest 16,000 characters of the transcript with attached file bodies reduced to names, 120 s timeout, never memoised) and opens a new conversation titled `Compacted: <old title>` whose first message is the summary; the old conversation is left unchanged, and a failed summary creates nothing (400 `COMPACT_EMPTY`, 502 `COMPACT_FAILED`).

Images can be attached from the composer: the attach button, pasting an image, or the file picker (png, jpeg, gif or webp, at most 4 per message and 5 MB each, enforced in the browser and again by `POST /api/images`, which also checks the file's magic bytes). Bytes are stored once by content hash in the state directory's `blobs/` folder and the message keeps only an `<attached_image id=...>` marker, so history stays small and replayable; thumbnails show in the composer and the transcript (`GET /api/images/:id`), the markdown export and

`/compact` name them as `image N` instead of embedding them, and each provider adapter sends them in its own wire format (OpenAI chat `image_url`, OpenAI responses `input_image`, Anthropic base64 `image` blocks, Gemini `inlineData`). A run is refused before any provider call when the catalog marks the chosen model `vision: false` (set it per model in a provider's `models`); a model the catalog does not flag is sent the image and any provider error is shown as is. `atelier run "<prompt>" --image <file>` (repeatable, at most 4) attaches png, jpeg, gif or webp files from the terminal with the same limits; every file is checked before a conversation is created.

A conversation can be forked: the Fork button on any message (or `/fork` for the whole conversation) calls `POST /api/sessions/:id/fork` and opens a new conversation titled `Fork: <title>` holding a copy of the messages up to and including that one, created in a single transaction so a crash leaves either the whole fork or nothing; the original is never changed, attachment markers are copied as text so images and files still resolve, and an empty conversation returns 400 `FORK_EMPTY`. On touch devices the message actions are always visible and at least 32 px tall.

Hooks run your own commands around the agent's tool calls. Define them in Settings (Hooks) or as `hooks: [{ id, event: "pre_tool" | "post_tool", match, command, timeoutMs }]` in `config.json`; `match` is a regular expression over the tool name (default `.*`) and `timeoutMs` is 100 ms to 60 s (default 10 s). Each hook runs in the workspace with `ATELIER_HOOK_EVENT`, `ATELIER_TOOL`, `ATELIER_TOOL_INPUT` (first 8,000 characters), `ATELIER_RUN_ID` and `ATELIER_SESSION_ID` set, and post hooks also get `ATELIER_TOOL_OK` and `ATELIER_TOOL_OUTPUT`. A `pre_tool` hook that exits with code 2 vetoes the call before any approval prompt: the model receives `Blocked by hook <id>: <its output>` and the tool never runs; any other exit code, a timeout or a hook that fails to start is only recorded. `post_tool` hooks never block. Every result is stored as a `hook.result` event. On narrow screens the workspace panel is now an opaque overlay.

`/init` sends a fixed prompt, always in Build mode, asking the agent to inspect the repository and create or improve `AGENTS.md` (facts it verified only, update rather than overwrite, under the 8,000-character cap that applies when instructions are injected into each run); the write goes through the normal edit approval. `/instructions` opens `AGENTS.md`, or `CLAUDE.md` when there is no `AGENTS.md`, in the Files panel, and points to

`/init` when neither exists.

Skills are reusable instruction bundles: a folder `.atelier/skills/<name>/SKILL.md` (or `.agents/skills/<name>/SKILL.md`, the folder Codex, Antigravity and Vibe use, or `.claude/skills/<name>/SKILL.md`, all of which atelier also reads; `.atelier` wins a name clash) with optional `name:` and `description:` frontmatter, at most 30 skills of 50 KB each, descriptions cut at 200 characters. The system prompt lists each skill's name, description and path, and tells the agent to read a skill with `read_file` only when it clearly matches the request, so nothing is loaded up front and there is no extra tool. Every skill is also a slash command (`/release fix the changelog` asks the agent to read that skill and follow it for the given task; an explicit command file with the same name wins), `GET /api/skills` lists them, and `/skills` shows what was found and refreshes the command menu.

Permission rules cut approval prompts in Build mode. Define them in Settings (Permission rules) or as `rules: [{ id, action: "exec" | "edit", match, decision: "allow" | "ask" | "deny" }]` in `config.json`; `match` is literal text with `*` as a wildcard, tested against the whole command or file path. A matching `allow` skips the approval prompt and a matching `deny` refuses the call without asking, even with `--yes`; a deny always beats an allow. An allow never covers a command containing `&&`, `||`, `;`, `|`, `&`, redirection, backticks, `$(` or a newline, nor a path containing `..`, so those still ask. Rules only decide whether to ask: secrets, paths outside the workspace and destructive commands are still blocked afterwards whatever the rules say. Each decision is recorded as an `access.decision` event naming the rule, and the approval dock's Always allow button approves the call and saves an exact-match allow rule (it is hidden for commands or paths no rule could cover, and nothing is approved if saving the rule fails).

`/model` shows the current default model and every model in the local catalog; `/model <id>` switches the default (provider and model, the same fields Settings writes) for the next message, keeping the current provider when two providers list the same id and refusing an id that is not in the catalog. Picking

`/model` from the menu inserts `/model ` for you to finish, and pressing Enter on a line whose first word is a known command runs it, while ordinary text and paths such as `/usr/bin` are left alone.

`/undo` restores the file from the newest checkpoint, the snapshot taken just before the agent's last checkpointed edit (a file the agent created has none, so nothing is restored for it), using the same restore as the History panel; because a restore snapshots the current file first, running

`/undo` again puts the edit back. It is refused while a run is working.

The status bar shows a context meter once a conversation has made a request: `ctx 33%` is the prompt size of the latest billed request (which already reflects automatic compaction) against the model's context window, taken from the built-in catalog or the `contextWindow` of the model in the provider's own `models` list. It turns amber from 70% and red from 90% and its tooltip then suggests

`/compact`; when the window is not known it shows a plain token count such as `ctx 12.3k` instead of guessing a percentage. `GET /api/usage` returns the same figure as `context` alongside the existing totals.

`/skill-new <name> [description]` creates `.atelier/skills/<name>/SKILL.md` from a template (frontmatter plus When to use, Steps and Notes sections), opens it in the Files panel for editing and refreshes the command menu so `/<name>` works at once. The name must be a plain folder name (letters, digits, `-` or `_`, at most 41 characters) and the description a single line of at most 200 characters; an existing skill in either skills folder is never overwritten (`POST /api/skills` answers 409 `SKILL_EXISTS`, and 400 for a bad name).

Safety details worth knowing: `@` mentions follow the same secrets policy as tools, so a file such as `.env`, `id_rsa`, `*.pem` or `secrets.json` is never attached even when you name it; the workspace path jail resolves symlinks and junctions, so a link inside the workspace cannot reach a file outside it (a path that cannot be resolved is refused); rule matching normalises paths (separators, `./`, `..`, repeated slashes, and case on Windows) and collapses whitespace in commands before comparing, so a deny rule cannot be dodged by how the call is spelled; and image blobs are written through a temp file, fsynced and renamed, and verified against their content hash when read, so a torn write is treated as missing and repaired on the next save.

Typing `@` in the composer suggests workspace files from `GET /api/workspace/files` (up to 5,000 paths, skipping `node_modules`, `.git`, build output and similar); basename matches rank first, Enter or Tab inserts `@path`, Esc dismisses. The path stays in the prompt text, so the agent reads the file through its normal `read_file` tool.

A conversation's cost and token totals include the sub-agents it delegated to (they run in their own hidden conversations); the Usage panel shows how much of the total came from them as `of which sub-agents`, and the context meter still reflects only the conversation's own latest request. The all-conversations total counts each request once.

Host checking: every request, including the page itself and the cookie bootstrap, must carry a Host header naming `localhost`, a `*.localhost` name or an IP literal (IPv4, or IPv6 in brackets, with any port), or a plain DNS name listed in `ATELIER_ALLOWED_HOSTS`. Anything else gets `421 HOST_REJECTED` and no cookie. A DNS-rebinding page reaches 127.0.0.1 under its own domain, so its Host is that domain and it is refused, while a LAN address or a listed reverse-proxy name keeps working. Wildcards, ports and paths in the list are ignored so a typo cannot widen access.

Sub-agent conversations: when the agent delegates a brief, the helper runs in its own internal conversation. Those are hidden from the conversation list, from search (by title and by message text), from `atelier sessions` and from `atelier run --continue`, so they can never be picked as the conversation to continue; they remain readable by id, which keeps run audits and the Task panel working, and their spend is counted in the parent conversation's totals.

Environment for agent commands: the agent's `bash` tool and MCP stdio servers run with the server's environment minus anything secret-shaped (a name in which KEY, TOKEN, SECRET, PASSWORD, PASSWD or CREDENTIAL(S) is a whole word, or that ends in APIKEY, AUTHTOKEN, ACCESSKEY, SECRETKEY or PRIVATEKEY) and minus each provider's `apiKeyEnv` variable. List variables a command legitimately needs, for example `GITHUB_TOKEN` or `NPM_TOKEN`, in `shellEnvPassthrough` in `config.json` (or `PUT /api/config`); the names are compared without regard to case, and an MCP server's own `env` entries are always passed. Hooks and the terminal panel keep the full environment because you wrote or run them. This removes one leak but is not a sandbox: an approved command still runs as you and can read your files, including `~/.atelier/secrets.json`, so treat the shell as unsandboxed.

Protected configuration: edits of `.atelier/`, `.claude/` and `.agents/` folders and of any file named `AGENTS.md` or `CLAUDE.md` (any depth, any spelling or case) are never auto-approved. A broad allow rule does not cover them, headless `--yes` refuses them for that call, and only a person approving in the UI can let the agent change them; a deny rule still refuses them outright. They steer every later run, so a prompt injection that could write one would persist.

Ask rules: a rule with `decision: "ask"` makes a matching call always ask a person. The order is deny, then ask, then allow, so `allow` for `git *` plus `ask` for `git push*` auto-approves everything except a push. An ask rule matches the way a deny does, so a chained command such as `npm test && git push` cannot slip past it, and nothing automatic can satisfy it: even headless `--yes` refuses a call an ask rule matched, and the approval prompt names the rule. Ask rules are set in `config.json` or through `PUT /api/config` for now; the Settings card still offers only allow and deny.
